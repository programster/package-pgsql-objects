This package aims to act as your object-relational-map (ORM) to a PostgreSQL 
database.

To use this package, we recommend you create two class files for each of your 
tables. One should end in the word `Table` and represent operations on the 
table itself. This should ideally extend `AbstractUuidTable` if the table uses 
UUIDs for its IDs, or `AbstractTable` otherwise. If you need to create 
something rather special, then one can just implement the `TableInterface` 
interface. Once you have extended the class, all you have to do is fill in all 
of the abstract methods.

The second class you need to create is for a row of the table. This class 
should extend the `AbstractTableRowObject`. Again, just fill in all of the 
abstract methods for the package to be able to manage your tables.


### IDs
Each table needs a single ID column. This is called `id` by default, but you 
can override `getIdColumnName()` to use another name, such as `uuid`.

Tables that extend `AbstractUuidTable` generate v7 UUIDs in code, which are 
time-ordered for good database index performance.

IDs are only ever generated for new rows: by `createNewFromArray()`, by the 
table's `insert()` and `batchInsert()`, and when an object is cloned. When a new 
row has no ID, the package chooses where its ID comes from in this order:

1. If `canCodeGenerateId()` returns true, the ID is generated in code by 
   `generateId()`, even if the database could also generate one.
2. Otherwise, if `canDatabaseGenerateId()` returns true, the ID is left for the 
   database to fill in, e.g. a `SERIAL` or `IDENTITY` column, or a default that 
   produces a new value per row, such as `gen_random_uuid()`. The object picks 
   up the generated ID when it is saved.
3. Otherwise, an exception is thrown, as the ID must be provided.

A few things to be aware of:

- `canCodeGenerateId()` must return false if the ID column is 
  `GENERATED ALWAYS AS IDENTITY`, as PostgreSQL rejects inserts that provide a 
  value for such a column. `GENERATED BY DEFAULT AS IDENTITY` is fine.
- `batchSave()` can save new objects whose IDs the database generates, which 
  have no ID until they are saved, alongside objects that already have one. It 
  inserts them with a single `MERGE ... RETURNING`, which tells it which 
  generated ID belongs to which object. This needs **PostgreSQL 17 or newer**. 
  On an older server, a batch containing any such objects throws an 
  `ExceptionUnsupportedDatabaseVersion` without saving anything, so save them 
  with `save()`, or insert their rows with the table's `batchInsert()`, 
  instead. Batches where every object has an ID work on any version.
- An object's ID can be changed through its `update()`, e.g. 
  `$user->update(['id' => $newId])`, which changes its row's ID too. Any foreign 
  keys referencing the old ID must allow it.


### Saving objects
There are two ways to save changes to your objects, depending on how many you 
are changing at once.

**One object, e.g. from a form:** call its `update()` with the new values. It 
always saves the object to the database straight away: it updates the row if 
the object has been saved before, or inserts it if it hasn't (e.g. a new object 
from `createNewFromArray()`). Every key is checked first, so a typo throws an 
`ExceptionUnknownColumn` without changing anything.

```php
$user = UserTable::getInstance()->load($id);
$user->update(['name' => $_POST['name'], 'email' => $_POST['email']]);
```

**Many objects at once:** change each object with its setters, which only 
change the object in memory, then pass them all to the table's `batchSave()`, 
which saves them in a single query. The query runs as one transaction, so 
either every object is saved, or none are.

```php
$table = ProductTable::getInstance();
$products = $table->loadWhereAnd(['category' => 'books'], CacheMode::USE_CACHE);

foreach ($products as $product)
{
    $product->setPrice($product->getPrice() * 2);
}

$table->batchSave($products);
```

So that you can do this, give your row classes setters that only set the 
value, and never call `save()`:

```php
class ProductRecord extends AbstractTableRowObject
{
    // ...

    # Setters
    public function setPrice(int $price) : void
    {
        $this->m_price = $price;
    }
}
```

A method that also saves isn't really a setter any more, and it would make 
`batchSave()` pointless, as each change would already have run its own query. 
If you want a one-step change and save for a single object, call `update()` 
instead, e.g. `$product->update(['price' => 200])`. If you really need a setter 
that can save, give it a parameter to choose, e.g. `setPrice(200, save: false)`, 
but keeping setters to just setting is simpler and less surprising.

Things to be aware of with `batchSave()`:

- New objects whose IDs the database generates are inserted with the rest, 
  and take on their generated IDs, but this needs PostgreSQL 17 or newer (see 
  [IDs](#ids)).
- For objects that already have an ID, it can't read back values the database 
  generates, such as column defaults or generated columns, so they will be out 
  of date on those objects until you reload them with 
  `CacheMode::UPDATE_CACHE`. New objects without an ID do take them on.
- Deleted objects are rejected before anything is saved.
- If a transaction is already open, it all runs within it.


### Key Features
- Saves/updates objects to the database for you when you want it to.
- Inserts many rows at once with `batchInsert($rows)`, in a single query, 
  returning the objects for them with any values the database generated, such 
  as `SERIAL` IDs, column defaults and generated columns. This works whatever 
  generates the IDs. The objects aren't necessarily in the same order as the 
  rows. To save many objects you already have, use `batchSave()`.
- Has an optional cache, so you don't re-fetch objects when you don't need to. 
  It's disabled by default, so every load gets fresh data from the database, 
  which is the safe choice for scripts and long-running processes. Enable it 
  for a table with `enableCache()` when it helps, such as in a web request:

  ```php
  // in the controller
  $users = UserTable::getInstance();
  $users->enableCache();
  $users->loadAll(CacheMode::USE_CACHE);

  // later, in a view or model, without a query
  $author = UserTable::getInstance()->load($post->getAuthorId());
  ```

  While it's enabled, there is only one object for each row: anything that 
  loads, inserts or saves a row uses that same object, so different parts of 
  the code never hold different versions of it. Every load takes a 
  `CacheMode`, saying how it uses the cache:

  - `CacheMode::USE_CACHE` returns rows that are cached as the cached objects, 
    as they are, and caches the rows it had to fetch. Loading a cached row by 
    ID doesn't query the database at all. This is the default for `load()` and 
    `loadIds()`.
  - `CacheMode::UPDATE_CACHE` fetches every row from the database, and updates 
    the cached objects with the rows' current values, in place.
  - `CacheMode::IGNORE_CACHE` fetches every row as a new object, and leaves 
    the cache alone.

  Queries that return many rows, such as `loadAll()` and `loadWhereAnd()`, 
  have no default, so you choose each time. The cache is never searched by 
  other columns: these queries always run, as only the database knows which 
  rows match, and with `USE_CACHE` the matching rows that are cached are then 
  returned as their cached objects. So a cached object with unsaved changes 
  can be returned by a filter it no longer matches. Use `UPDATE_CACHE` or 
  `IGNORE_CACHE` when you need the database's values. Call `disableCache()` to switch 
  the cache off and empty it. If your server keeps PHP 
  running between requests (e.g. FrankenPHP's worker mode, RoadRunner or 
  Swoole), call `disableCache()` at the end of each request, so the cache 
  doesn't carry over into the next one.
- Supports pagination in two ways:
  - `loadRange($offset, $numElements, $cacheMode, $orderByColumn)` loads a page by offset, 
    ordered by the ID column by default, or by the column you pass (with the ID 
    column as a tiebreaker). Rows inserted or deleted before the current page 
    will shift later pages.
  - `loadAfterId($afterId, $numElements, $cacheMode)` loads the rows whose IDs come after 
    `$afterId`, in ID order. Pass `null` for the first page, then the ID of the 
    last object on each page to load the next, until an empty page is returned. 
    This never skips or repeats rows when rows are inserted, updated, or deleted 
    between pages, and stays fast however deep into the table you go, so prefer 
    it for processing every row in a table.
- Supports cloning of the objects. The clone is marked as not being in the 
  database, and gets a new ID generated in code, or one from the database when 
  it is saved. It will only be persisted if you save it to the database.
- Converts integer, float, and boolean columns (including integer IDs) to their 
  PHP types when loading rows. If converting a column would lose information, 
  such as a high-precision `numeric` column becoming a float, list it in your 
  table's `getFieldsToKeepAsString()` to keep the exact string from the 
  database instead. `money` columns are always kept as strings, as PostgreSQL 
  formats them for its locale.
- Supports virtual fields, which are columns whose values PostgreSQL always 
  computes itself, such as PostgreSQL generated columns (both 
  `GENERATED ALWAYS AS (...) STORED` and `VIRTUAL`), or non-ID 
  `GENERATED ALWAYS AS IDENTITY` columns. List them in your table's 
  `getVirtualFields()`, and they won't be required when creating 
  objects, will never be sent in inserts or updates, and will be read back from 
  the database after `save()`, `update()`, `insert()` and `updateById()`. `batchSave()` can't 
  read them back, so reload the objects with `CacheMode::UPDATE_CACHE` if you 
  need their new values.

## Testing
The package is tested against every supported major version of PostgreSQL 
(14 to 18). To run the tests against all of them, each in a throwaway docker 
container that is removed afterwards, run:

```bash
testing/run-all-versions.sh
```

Or pass the versions to test, e.g. `testing/run-all-versions.sh 16 18`. It 
needs docker and bash (on Windows, Git Bash or WSL), and uses ports 5454 to 
5458 (5440 plus the version).

The tests also run on GitHub Actions, for pushes to `main` and `5.x`, every tag, 
and pull requests into either, which is what the badges at the top of this 
README show, with a row for each branch:
- **Linux** (`.github/workflows/tests.yml`): runs `testing/run-all-versions.sh`
  on PHP 8.2, 8.3, 8.4 and 8.5.
- **macOS and Windows** (`tests-macos.yml` and `tests-windows.yml`, which share
  `tests-native.yml`): GitHub's runners for these can't run the Linux PostgreSQL
  images, so each supported version of PostgreSQL is installed on the runner 
  directly, and tested on PHP 8.5.
- **WSL** (`tests-wsl.yml`): PHP 8.3 in WSL, against PostgreSQL 18 on the 
  Windows side. GitHub's Windows runners only have WSL 1, so WSL 2 isn't tested.

Each run also lists its results and any failed tests as annotations on the run's 
summary page. They can be run by hand on any branch with "Run workflow" on the 
repository's Actions tab.

To run the tests against a single database instead, they need one that they 
are free to empty, as they create tables and truncate them. On PostgreSQL 
older than 18, the test table's virtual generated column is created as a stored 
one instead, and on PostgreSQL older than 17, the tests check that 
`batchSave()` rejects objects without IDs. You can run a throwaway database 
through docker with:

```bash
docker run -d \
  --name pgsql-objects-test \
  -e POSTGRES_USER=test \
  -e POSTGRES_PASSWORD=test \
  -e POSTGRES_DB=pgsql_objects_test \
  -p 127.0.0.1:5433:5432 \
  postgres
```

Then fill in your PostgreSQL connection details (including `DB_PORT`, which is 
`5433` for the container above) into the `/testing/settings.php.tmpl` file and 
rename it to `/testing/settings.php`. Any of them can also be set with an 
environment variable of the same name prefixed with `TEST_`, e.g. 
`TEST_DB_PORT=5433`, which takes precedence over `settings.php`.

Then run the tests with:

```bash
php testing/main.php
```
